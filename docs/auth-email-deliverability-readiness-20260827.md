# MtaaMarket authentication-email deliverability readiness

**Decision date:** 27 August 2026  
**Scope:** Password-account verification and recovery codes only. This record does not change Supabase Auth settings, send email, create an account, configure an SMTP provider, access a domain registrar, add DNS records, or activate public invitations.

## Current assessment

MtaaMarket’s password-first account interface is ready to use six-digit codes only when a new password account must be verified or a password is being recovered. That interface must not be represented as production-email evidence while the site relies on the default Supabase SMTP service. Supabase documents that the default service is intended for exploration and testing, only delivers to pre-authorized project-team addresses, is currently limited to two messages per hour, and provides no delivery or uptime service-level assurance.[1]

The previously verified temporary SMTP sender provides a guarded testing path, but Spam placement is not proof of an inbox-placement solution. It remains a temporary testing configuration, not a public-launch approval. The UI continues to give code-specific Spam/Junk guidance, contains no promotional email content, and does not expose passwordless sign-in or public invitation flows.

| Area | Current decision | Why it remains bounded |
|---|---|---|
| Public account model | Retain email/password for returning users; use a six-digit code only for signup verification and recovery. | This remains the implemented product decision and avoids a new authentication provider. |
| Default Supabase SMTP | Do not treat it as a public delivery channel. | It is team-address restricted, heavily rate limited, and documented as non-production.[1] |
| Existing temporary sender | Retain only as a controlled test configuration. | A temporary sender and a Spam-folder recovery tip do not establish durable sender reputation. |
| Custom SMTP | Defer configuration until the founder controls a suitable sender domain and directly supplies provider credentials through the secure project setting. | SMTP host, username, password, and from-address are provider credentials and must not be entered in source code or chat. |
| Supabase project custom domain | Do not configure it as part of this zero-cost sender-domain step. | Supabase documents project custom domains as a paid add-on; they are distinct from authenticating a domain with an SMTP provider.[2] |

## Required later controlled activation

Once the founder owns and controls a MtaaMarket domain, the proper next step is to select an SMTP provider that supports authenticated sending, then use a dedicated authentication subdomain and sender address, for example `auth.<founder-domain>` and `no-reply@auth.<founder-domain>`. Supabase recommends separating authentication mail from marketing mail and setting up SPF, DKIM, and DMARC through the sending provider.[1]

The founder must copy the DNS records generated by the selected SMTP provider exactly into the domain’s DNS zone and wait for the provider to verify them. Only then should the sender identity and SMTP credentials be entered through the Supabase Authentication SMTP settings. Supabase states that custom SMTP enables delivery to all addresses, after which its Auth server applies a 30-message-per-hour protective rate limit until the project rate limit is reviewed.[1]

> **Operational boundary:** A MtaaMarket website domain on Vercel, an SMTP sender domain, and a Supabase project custom domain are separate configurations. The first two do not authorize a supplier feed, payment, delivery commitment, AI connection, or a change to the account model. The third is a paid Supabase add-on and is not required simply to authenticate an SMTP sender domain.[1] [2]

The only acceptable activation evidence is one founder-controlled signup-code delivery and verification test plus one recovery-code delivery and reset-completion test, conducted in an existing private browser session. The record must contain only pass/fail results and high-level inbox placement; it must not include an address, password, code, link, token, or message contents. No public invitations should be activated as part of that test.
